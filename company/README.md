# 株式会社サクシス（SX指数事業部）

競馬指数「サクシス（SX）」を改善し、販売できる商品にするための仮想会社です。
社長と社員はすべて Claude Code のエージェント（`.claude/agents/`）として動きます。

## 組織図

```
社長  sx-president（全体方針・採否判断・販売可否の最終判断）
 ├─ データ分析部  sx-data-analyst      成績ログから弱点・強みを見つける
 ├─ 指数開発部    sx-index-engineer    SXの計算式・グレード基準の改善案を作り、実装する
 ├─ 検証部        sx-backtest-auditor  改善案を独立に検証する（過剰最適化・サンプル不足を止める）
 └─ 商品企画部    sx-sales-planner     商品設計・価格・販売ページ・法令チェック
```

社員は社長からの指示でだけ動き、社員同士は直接やりとりしません。報告はすべて社長に上がります。

## 動かし方

| 方法 | コマンド |
| --- | --- |
| Claude Code（PC）で社長として起動 | `claude --agent sx-president` |
| どこからでも（Web・アプリ含む） | 会話で `/sx-shacho 今週の改善会議をして` |

社長への頼み方の例:

- 「今週の改善会議をして」… 分析部→開発部→検証部の順に回し、採否と次の一手を報告
- 「グレードSの基準を見直して」… 特定テーマの改善
- 「販売開始できる状態か判定して」… 販売判定基準に照らして可否を出す
- 「販売ページの下書きを作って」… 商品企画部が作り、検証部が数字を確認

## 共通ルール（全社員）

1. **数字は `tools/sx_kpi.py` で出す。** 手計算・記憶の数字を報告に書かない。
2. **サンプル数を必ず添える。** 100レース未満の結果は「参考値」と明記する。
3. **オッズ欠損の扱い。** 現状のログは◎が勝ったレースにしか `ai_top1_odds` が入っておらず、そのまま回収率を出すと大きく上振れする。`sx_kpi.py` はオッズ記録率90%未満の区分では回収率を出さない。回収率で語りたいときは、まず外れたレースの◎オッズも記録する（データ整備が先）。
4. **改善案は「仮説→変更→検証」の順。** 検証部の合格なしに本番の指数を変えない。
5. **販売物に「必ず儲かる」「的中保証」等は書かない。** 過去成績は期間・レース数・条件を必ず併記する。
6. 会議の結果は `company/reports/YYYY-MM-DD_テーマ.md` に残す。

## KPI と販売判定基準（社長が使う）

| 項目 | 販売開始の目安 |
| --- | --- |
| 評価対象レース数 | 1,000レース以上（最低でも3か月分） |
| ◎単勝回収率（オッズ判明分） | 期間を分けた前半・後半の両方で 100% 超 |
| ◎複勝率 | 全体で 40% 以上、かつ大きく崩れる月がない |
| グレード序列 | S > A > B > C の順に的中率が並ぶ |
| 再現性 | 改善後の式を「改善に使っていない期間」で検証して合格 |

基準を変えるときは社長が理由をつけて、この表を更新します。

## データの場所

- 成績ログ: `daily_results_log.json`（`days[].races[]`）
- ダッシュボード: `streamlit run dashboard.py`
- SX本体（計算式・`sx_run` 等）はTARGETがあるPC側にあります。開発部が式を変えるときは、そのコードがこのセッションにあるか最初に確認し、無ければ「変更案（差分の形）」として社長に出します。
